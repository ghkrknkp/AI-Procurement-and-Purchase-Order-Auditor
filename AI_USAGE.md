# AI Usage Disclosure

This document provides an honest account of how AI tools were used in building the **AI Procurement and Purchase Order Auditor** application.

---

## AI Tools Used

| Tool | Purpose |
|------|---------|
| **Google Gemini (Antigravity)** | Primary development assistant — architecture, code generation, debugging |

---

## How AI Was Used

### 1. Architecture and Design
- AI helped design the layered architecture: FastAPI backend → SQLAlchemy ORM → SQLite, and React/TypeScript frontend with role-based access.
- The workflow state machine (DRAFT → SUBMITTED → APPROVED/REJECTED) and RBAC model were designed with AI guidance, then reviewed and refined.
- Database schema (7 models: User, Document, ExtractedField, PurchaseOrder, PurchaseOrderItem, ReviewComment, WorkflowHistory) was co-designed.

### 2. Code Generation
- **Backend:** FastAPI routers, SQLAlchemy models, Pydantic schemas, security utilities (bcrypt + PyJWT), Alembic migration setup, and service layer (extractor, validator, matcher, audit) were largely generated with AI assistance.
- **Frontend:** All React components and pages (Login, Register, Dashboard, DocumentsList, DocumentUpload, DocumentDetail) were generated with AI assistance, including TypeScript types, Axios API client with JWT interceptor, and Tailwind CSS styling.
- **Tests:** Pytest test suites for auth, extraction/validation, PO comparison, and workflow RBAC were generated with AI guidance.

### 3. Problem Solving and Debugging
AI assistance was critical for resolving several non-trivial issues:
- **PyMuPDF DLL blocked by Windows App Control policy** — The `_mupdf` native DLL was blocked by system policy. AI identified the issue and implemented a `try/except ImportError` fallback to `pypdf` (pure Python), keeping the system functional.
- **Pydantic v2 migration warnings** — AI identified that `class Config` style is deprecated in Pydantic v2 and explained why it still works.
- **TypeScript `verbatimModuleSyntax` errors** — AI identified and fixed all type-only imports to use `import type { ... }` syntax.
- **Alembic `env.py` customization** — AI customized the default `env.py` to use `settings.DATABASE_URL` and import all SQLAlchemy models correctly for migration generation.
- **Email validation dependency** — `pydantic[email]` requires `email-validator`; AI caught the missing dependency and updated `requirements.txt`.

### 4. Boilerplate and Scaffolding
- Project structure, `.gitignore`, `.env` / `.env.example` files, `pytest.ini`, and `tailwind.config.js` / `postcss.config.js` were generated by AI.
- Seed data script (`seed.py`) and sample document generator (`generate_samples.py`) were AI-generated.

## What Was NOT AI-Generated / Human Decisions

| Decision | Rationale |
|----------|-----------|
| **Technology stack selection** | Chosen per assessment requirements (FastAPI, React, SQLite, Tailwind) |
| **Rule-based PO comparison** | Deliberate choice to use deterministic tolerance-based matching (+/-0.05) rather than a language model, for auditability and reproducibility |
| **pypdf as PyMuPDF fallback** | Human decision after encountering the App Control policy block — ensures the system works in restricted environments |
| **No external AI API calls at runtime** | All document processing (extraction, validation, matching) is done locally; no OpenAI/Gemini API calls are made during invoice processing |
| **SQLite for storage** | Chosen for zero-config local setup appropriate for a technical assessment |
| **Demo credential design** | Two roles (submitter + reviewer) with clear separation to demonstrate RBAC |

## AI Limitations Acknowledged

- **Invoice extraction is regex/rule-based**, not LLM-based. A production system would use a dedicated document AI (e.g., Google Document AI, AWS Textract, or a fine-tuned model) for higher accuracy on varied invoice formats.
- **PO comparison uses fixed tolerance thresholds**, not semantic understanding. Production systems might use fuzzy matching for vendor/item names.
- **OCR support requires Tesseract** installed system-wide. In this environment, Tesseract was not installed, so OCR falls back gracefully to text-based extraction only.
- **AI-generated code was reviewed** for correctness but not exhaustively tested against all edge cases. The 16 automated tests cover the primary happy paths and key RBAC boundaries.

## Honest Assessment

The AI assistant significantly accelerated development — tasks that would take days were completed in hours. However, AI-generated code required human review, debugging, and iteration. The most valuable AI contributions were:
1. Generating boilerplate that would otherwise be tedious (schemas, migrations, TypeScript types)
2. Debugging environment-specific issues (DLL policy blocks, dependency conflicts)
3. Maintaining consistency across a large codebase (naming conventions, API contract alignment)

The core business logic (validation rules, PO matching algorithm, workflow state machine) was designed with AI assistance but reflects deliberate architectural choices appropriate for a procurement audit use case.
